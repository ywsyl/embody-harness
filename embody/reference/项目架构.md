整体模块（角色名以各角色实现文档为准；"只"指职责边界：编排器不直接调工具、执行器不决策业务）：

2、编排器 Orchestrator（agent）：只负责编排任务——理解任务、就绪检查、产出并校验 Program、按需修复/重规划，见 Orchestrator/orchestrator_implementation_latest.md

1、交互器：交互记录、待满足信息需求（pending requirements）；信息来源：云端/用户、编排器、监督器（均经总线）
2、编排器：任务状态 + 当前 Program 状态；外部更新来源：交互器（任务指令/交互结果）、监督器（program_error / replan_required / capability_changed）；自身决策也会改状态
3、监督器：具身工具/能力状态（Capability State）；信息来源：执行平面内的本地观察（工具调用/结果/健康/观测），不接收来自其他 Agent 的业务指令（安全 STOP 由本地安全信号触发）

# 附录：基于 deepseek-harness 的落地分析（2026-09-08）

## 1. 技术路线（已选定：dsh 当引擎，Python 做薄层）

`deepseek-harness`（下称 dsh）= DeepSeek 开源的 **Cordis 插件化 agent harness**，引擎主体是 **TypeScript**（`@deepseek-ai/dsh-*` 包）；Python 侧只有一个薄客户端 `deepseek_harness`，经 stdio JSON-RPC 驱动打包的 `dsh` 可执行文件。

关键前提：

- dsh 引擎**已内建**：类型化事件 + 会话事件日志、agent-loop、工具注册/解析/执行、LLM 服务抽象、交互/审批（ask-user、approval）、子代理委托、goal/todo/plan/进度投影、skill/guard/telemetry、workflow…… 本架构图中大量"代码模块"在引擎里已存在，**无需用 Python 重写**。
- 因此本项目的实现方式：**每个角色（Interactor / Orchestrator / Supervisor）= dsh 一个独立 Session**（各自的工具集、上下文、事件日志），角色间靠共享文件（`runtime/files/*`）+ 事件解耦（正好符合顶部"避免耦合、文件相互引用"的原则）；**新增领域能力做成 dsh 插件（TS）**；**Python 薄层只做三件事：跨角色协调、vision 观察、把共享状态文件化**。

目录布局示意：

```text

├── python/                # 薄层（依赖 deepseek_harness-sdk）
│   ├── coordinator.py     # 起停各角色 Session、路由事件、搬运共享文件
│   ├── interaction_agent.py / orchestrator.py / supervisor.py  # 各角色 Session 入口（按 preset 组合工具集）
│   └── vision_observer.py # 新写：截图 → 图像归一化 → 写 vision_obs.yaml
├── dsh-plugins/           # 新增 TS 插件
│   ├── program-dsl/       # Program/DSL 定义 + 产出工具
```

> 复用的**核心惯用法**：事件是唯一事实源（`SessionEventMap` + 会话日志），进度/状态是"投影"（`SessionProjectionMap`）；一切可调参数是校验过的插件 Config，策略是数据不是代码。

## 3. 必须新写的部分（dsh 没有）

1. **`runtime/scripts/vision_observer.py`** —— 截图、屏幕/环境观察能力，全仓确认无现成工具。
2. **Program / DSL 本体 + `logic_validator.py`**（控制流、变量、分支静态检查）—— dsh 无"程序即产物 + 静态分析"层；workflow 是最接近的"模型写脚本→validateMeta→执行"范式。
3. **`references/` 顶层策略文件机制** —— dsh 用插件配置/registry 而非 yaml 清单（yaml 仅作为喂给模型的提示文本）。
4. **Python 侧的 typed-event 注册表 / 任务进度模型** —— python SDK 只是 JSON-RPC 客户端，这些模型都在 TS 引擎里。

## 4. 哪些规划代码应从 .py 改为 TS（取舍结论）

判定规则：**代码越靠近"模型 / 工具 / 事件管线"，就越该放 TS（与引擎同进程、单一 schema 源）；代码越靠近"真实世界边界"（屏幕、外部文件、GUI 自动化），越适合 Python（vision 尤甚）。**

推荐改为 TS（做成 dsh 插件）：

| 原规划 .py | 改为 TS 的原因 |
|---|---|
| `core/event/event.py`、`event.json` | 引擎事件总线/生成在 TS，Python 只能"订阅"，写类型会与引擎漂移 |
| `core/task/*.py` | 任务状态是引擎投影，Python 侧再造一套 = 双份维护 |
| `core/tool/*.py` | 引擎整包提供，Python 只消费 |
| `Orchestrator/validator/*`（schema/tool/logic）| 校验须挂在 `tools/execute` 之前的插件水槽里，错误信息直接回喂模型同一进程；schema 需与模型所见同源（typert/JSON Schema） |
| Program/DSL 定义 + 产出工具 | 模型在引擎里产出程序，工具注册、schema 生成、类型图都在 TS |
| `Interactor/` 里深逻辑（requirement 状态机）| 可挂 goal/todo/approval 现成状态，深逻辑在 TS 与事件同源 |

**保留 Python**：

| 保留 | 原因 |
|---|---|
| `runtime/scripts/vision_observer.py` | 截图/图像生态（Pillow/OpenCV/mss/pyautogui）Python 更成熟 |
| 跨角色协调/文件胶水（薄层本身） | 只需读文件 + 调 SDK；不参与模型-工具管线 |
| 任何独立于引擎的离线脚本 | 避免为小工具引入 TS 构建链 |

净效果：绝大多数"领域代码"落进 TS 后，与引擎单进程互操作，**消除进程边界上的 schema 重复与序列化往返**；Python 只留在真实世界边界上，保持薄。
